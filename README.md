# TIGER vs SASRec

[![CI](https://github.com/alina0607/tiger-vs-sasrec/actions/workflows/ci.yml/badge.svg)](https://github.com/alina0607/tiger-vs-sasrec/actions/workflows/ci.yml)

This repository is first of all a study in Python design. It builds a real machine-learning
pipeline, two sequential recommenders compared on the same data, and uses that pipeline as the
reason for every design choice: my own decorators, a metaclass, an inheritance hierarchy and a
context manager, each written for a concrete need. The models themselves use PyTorch.

> **Status:** work in progress. Steps 1–7 of the [roadmap](#roadmap) are done; every number
> in this README is taken from a run.

## Python design

| Feature | Where | What it is for |
|---|---|---|
| Metaclass | [`recsys/registry.py`](recsys/registry.py): `RecommenderMeta(abc.ABCMeta)` | Registers each model by name (`scripts/run.py --model popularity`), checks `name` and `config_cls` when the class is defined, and checks each model after its whole `__init__` chain has run, which `__init_subclass__` cannot do |
| Abstract base classes, template method | [`recsys/base.py`](recsys/base.py): `Recommender` → `ScoringRecommender` → [`PopularityRecommender`](recsys/models/popularity.py), [`SASRec`](recsys/models/sasrec.py) | A scoring model writes only `fit` and `score_all`; removing items the user already has and taking the top k are shared. A generative branch for TIGER joins later without changing evaluation |
| Wrapping decorator | [`recsys/decorators.py`](recsys/decorators.py): `@timed` | Records how long each call takes in the active run log; `functools.wraps` and `ParamSpec` keep the signature for callers and for mypy |
| Registering decorator factory | [`recsys/metrics.py`](recsys/metrics.py): `@metric("recall")` | Adds a metric to a registry and returns the function unchanged; a duplicate name fails at import. Evaluation computes every registered metric, so adding one needs no change there |
| Context manager with a `ContextVar` | [`recsys/runlog.py`](recsys/runlog.py): `with RunLog() as log:` | Makes one run log active for the current thread or asyncio task; nested runs restore the outer log, even when the block raises. It records which model was built (the metaclass adds it), how long each step took, and the scores, and is saved as JSON under `runs/` |
| Frozen dataclasses, `NamedTuple` | [`recsys/config.py`](recsys/config.py), [`recsys/data.py`](recsys/data.py): `Split`, `Review`, `RemoteFile` | Configurations and data splits cannot change after they are built, so the values recorded for a run are the values it used |
| Context manager that is also a decorator | [`recsys/decorators.py`](recsys/decorators.py): `with seeded(67):` (`contextlib.contextmanager`) | Seeds `random` and `torch` (CPU, MPS, CUDA) for one block and restores the previous state afterwards, even when the block raises; the seed lives in the model's configuration, so the run log records it |
| Composition (*has-a*) | [`recsys/models/sasrec.py`](recsys/models/sasrec.py): `SASRec` has a `SASRecNet(nn.Module)` | `SASRec` *is a* `ScoringRecommender` and *has a* network, instead of inheriting from both `Recommender` and `nn.Module`, whose `__init__` and `__setattr__` rules would otherwise mix |
| Planned | `@disk_cache(...)` (step 8) | Caching slow steps with `hashlib` + `pickle` |

Full-ranking evaluation ([`recsys/evaluate.py`](recsys/evaluate.py)) is a free function rather
than a method on `Recommender`, so no model can override how it is scored.

## Class diagram

**[Open the class diagram](https://alina0607.github.io/tiger-vs-sasrec/classes.html)**: the
package's classes and how they relate, drawn by [cartograph](https://github.com/alina0607/cartograph)
from the source and served by GitHub Pages. Drag boxes, bend lines, pan and zoom; a reload
returns to the saved layout. [`docs/classes.seed.json`](docs/classes.seed.json) holds the same
classes and relations as data, so a diff shows what a change added. Functions are hidden until
you press **functions**.

The saved layout lives in `docs/classes.layout.json`: arrange the board, press **save**, and put
the download there. Without that file, cartograph lays the board out itself.

Both files are regenerated by `scripts/update_diagram.py`, which runs on every commit that
touches `recsys/` (see below). The diagram leaves out the tests; to draw them too:

```bash
uv run python scripts/update_diagram.py --with-tests   # writes docs/classes_with_tests.* (untracked)
```

## CI/CD and automated checks

### Before every commit: pre-commit

Install once per clone with `uv run pre-commit install`; the hooks are defined in
[`.pre-commit-config.yaml`](.pre-commit-config.yaml).

| Hook | Source | What it checks |
|---|---|---|
| `trailing-whitespace`, `end-of-file-fixer` | pre-commit-hooks v6.0.0 | Whitespace at line ends and a final newline |
| `check-yaml`, `check-toml` | pre-commit-hooks v6.0.0 | YAML and TOML files parse |
| `check-added-large-files` | pre-commit-hooks v6.0.0 | No file over 1 MB is committed (the data stays out of git) |
| `ruff-check --fix`, `ruff-format` | ruff-pre-commit v0.17.5 | Lint and formatting |
| `mypy` | local, `uv run mypy recsys tests scripts` | Static types, run in the project environment so it sees the real dependencies |
| `class-diagram` | local, `uv run python scripts/update_diagram.py` | Redraws `docs/classes.*` when a file in `recsys/` or the saved layout changes, and stops the commit if the diagram moved so the new version can be reviewed and added |

### On every push and pull request: GitHub Actions

[`.github/workflows/ci.yml`](.github/workflows/ci.yml) runs on Ubuntu with Python 3.12 and uv
0.11.15 (with its cache), with read-only repository permissions and a 15-minute timeout:

| Step | Command | Fails when |
|---|---|---|
| Install | `uv sync --locked` | `uv.lock` no longer matches `pyproject.toml` |
| Lint | `uv run ruff format --check .` and `uv run ruff check .` | Formatting or lint errors |
| Type check | `uv run mypy recsys tests scripts` | A type error |
| Test | `uv run pytest` | Any test fails (the tests that need the downloaded data are skipped) |
| Class diagram is up to date | `uv run python scripts/update_diagram.py`, then `git status -- docs/` | A commit changed `recsys/` without the redrawn diagram |

### Deployment: GitHub Pages

GitHub Pages serves the `docs/` folder of the `dev` branch at
<https://alina0607.github.io/tiger-vs-sasrec/>. Every push to `dev` triggers GitHub's
**pages build and deployment** workflow, so the published class diagram always matches the
latest commit (the CI step above guarantees `docs/` is current).

### Reproducibility

- **Dependencies** are pinned in `uv.lock`; CI installs with `--locked`.
- **PyTorch** comes from the CPU wheel index on Linux, so CI does not download CUDA libraries.
- **cartograph** is pinned to a full commit SHA in `pyproject.toml`, so the diagram does not
  change unless the pin does.
- **Data** is checked on download by size and SHA-256 (`recsys/data.py`), so everyone runs on
  the same bytes.

## The two models

Two ways to recommend the next item a shopper will buy, built from scratch and compared on the same data:

| | **SASRec** | **TIGER** |
|---|---|---|
| Paper | Kang & McAuley, *Self-Attentive Sequential Recommendation*, ICDM 2018 ([arXiv:1808.09781](https://arxiv.org/abs/1808.09781)) | Rajput et al., *Recommender Systems with Generative Retrieval*, NeurIPS 2023 ([arXiv:2305.05065](https://arxiv.org/abs/2305.05065)) |
| Transformer | Decoder only, causal self-attention | Encoder-decoder (T5 style) |
| An item is | An atomic ID with its own learned embedding | A Semantic ID: a few codes computed from the item's text (Sentence-T5 vector, then RQ-VAE), so similar items share leading codes |
| How it picks the top 10 | Scores every item (dot product with the user's state) and keeps the 10 highest | Writes the next item's Semantic ID one code at a time (beam search), then looks the item up |
| Kind of retrieval | Scoring and ranking | Generative retrieval: the model's weights act as the item index |
| New items | Cannot recommend an item it never saw in training | Can, since a new item gets a Semantic ID from its text (shown in the paper on Beauty only, Section 4.3) |

## Data and results

Amazon review data (2014 release), **Beauty** category, 5-core, the same data TIGER uses
(22,363 users, 12,101 items, mean sequence length 8.87; TIGER Table 6).

- Split: leave-one-out per user (last item = test, second to last = validation).
- Metrics: Recall@5/10 and NDCG@5/10, ranking against **all** items.
- The data is not included in this repository. `uv run python scripts/prepare_data.py` downloads
  it from the [dataset page](https://cseweb.ucsd.edu/~jmcauley/datasets/amazon/links.html),
  checks it and prints the statistics above; please cite the dataset authors if you use it.

Why this dataset: TIGER Table 1 reports both TIGER and SASRec on it under the same full-ranking
evaluation, so my numbers can sit next to published ones.

| Beauty | Recall@10 | NDCG@10 | Source |
|---|---|---|---|
| SASRec | 0.0605 | 0.0318 | TIGER paper, Table 1 |
| TIGER | 0.0648 | 0.0384 | TIGER paper, Table 1 |
| TIGER (independent reimplementation) | 0.0594 | 0.0321 | [XiaoLongtaoo/TIGER](https://github.com/XiaoLongtaoo/TIGER) |
| Popularity (this repo) | 0.0115 | 0.0055 | `scripts/run.py --model popularity` |
| SASRec (this repo) | 0.0539 | 0.0281 | `scripts/run.py --model sasrec`, seed 67, stopped at epoch 160 (best validation at 110) |
| TIGER (this repo) | – | – | not run yet |

## Development

Python 3.11 or newer, managed with [uv](https://docs.astral.sh/uv/). `uv sync` creates the
environment from `uv.lock`, including the development tools. The same checks CI runs:

```bash
uv sync
uv run pre-commit install           # once per clone
uv run ruff format --check .        # formatting
uv run ruff check .                 # lint
uv run mypy recsys tests scripts    # type check
uv run pytest                       # tests
```

Run a model end to end (download and check the data, fit, score the validation and test cases,
save the run log to `runs/`):

```bash
uv run python scripts/run.py --model popularity
uv run python scripts/run.py --model sasrec     # about 10 minutes on an Apple M-series GPU (MPS)
```

## Roadmap

1. Package skeleton and test setup (pytest, ruff, mypy, CI)
2. Model registry (metaclass) and base classes
3. Decorators
4. Data download and preprocessing (check: 22,363 users, 12,101 items)
5. Metrics and full-ranking evaluation
6. Popularity baseline
7. SASRec
8. Item text embeddings (Sentence-T5)
9. Semantic IDs with residual k-means
10. TIGER: sequence-to-sequence model and constrained beam search
11. RQ-VAE Semantic IDs, three seeds, results table
